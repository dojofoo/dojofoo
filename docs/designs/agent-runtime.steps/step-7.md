## What this step delivers

Course evaluation runs inside the UI server. A trial is a throwaway learner install of the draft (`createLessonTrial`, kind `evaluation-trial`) on the draft's coding agent and model. Its Sensei host runs with a per-trial usage ceiling and stops when the trial ends. The simulated learner acts through the same HTTP routes a learner's page uses: `POST /sessions/default` opens the conversation and sends the begin turn, messages and answers go through the session API's `/eve/*` proxy (so the pre-delivery hook opens guard windows), and saves, Checks and the "Open next lesson" step go through the lesson routes (so check reports reach Sensei as server-sent turns). The solution fixtures, the learner's replies and both judge panels are one-shot calls (`oneShot`, a new harness export over `generateText` and the harness model in `read-only` mode) on the course's agent. `.dojo/evaluation-settings.json` keeps only consent; the per-role pickers, `/models` and `HarnessModelInput` go. Kyoshi's evaluate tool calls host-port `evaluation.start`, polls `evaluation.status` and cancels with `evaluation.cancel`. Every offered agent, Pi included, can now be evaluated.

Then the ACP stack goes: the evaluation worker (`teaching-eval.ts`, `fixture-preflight.ts`, `authoring-handoff.ts`, `evaluation/host.ts`), `dojofoo kyoshi evaluate`, the ACP lesson functions and routes, `codex-client.ts`, `agui-stream.ts`, `packages/ui/src/server/harness/`, the run coordinator, `lesson-mcp.ts`, the registry's `acp` field with `acpAgentIds` and `isAcpAgentId`, the `@agentclientprotocol/*` and `@modelcontextprotocol/sdk` dependencies and the `@tanstack/ai-client` patch. The evals that used the deleted code move onto the harness and onto the UI server's evaluation. `docs/architecture/agent-runtime-consolidation.md` and `docs/architecture/run-coordinator.md` are marked superseded.

## The trial (`packages/ui/src/server/evaluation/trial.ts`)

The stages, questions, evidence and failure rules are `authoring-handoff.ts`'s (fact 2), ported onto the channel and the roles. In order:

1.  **Install.** `evaluations.run` has made the evidence folder. `createLessonTrial(draftRoot, lessonIds[0], { agent: resolveAgent(draftRoot), model: readAgentModel(draftRoot, agent), kind: "evaluation-trial" })` (decision 13). The evidence folder is `<draft>/.dojo/handoffs/run-*` as today (`authoring-handoff.ts:62-64`); the trial's first entry is `{ learnerProfile: "struggling", priorLessons: "seed-completion", maxTeachingQuestionReplies, harness: agent, model, turnIntervalMs }` and the second `{ trialWorkspace }`. The installed material is read with `readMaterial(dojoDir(trialRoot, courseId))` and saved as `installed-material.json`.
2.  **Fixtures.** `roles.fixtures(lessonIds, readLessonMaterial(draftRoot, lessonIds))`: one one-shot per lesson with `fixtureGeneratorInstructions` and `fixturePrompt`, parsed with `parseGeneratedFixture`. For each lesson, in the trial install, inside `withPathLock(path)`, the trial writes `wrong` with `writeFileAtomic`, runs `runLessonTests` (Commit 2), writes `solved`, runs it again, then writes the original back or, when the lesson had no file, unlinks it (`fixture-preflight.ts:29,48-50`), so `advanceLesson` still scaffolds an unvisited lesson (`service.ts:463`). It does not use `writeSolution`, which records the lesson as active (`service.ts:385-393,425-432`); no window is open, since no Sensei session exists yet. `wrong` must fail a test and `solved` must pass every test, or the trial fails with "Learner fixture preflight failed: <lesson>/<variant>: …" and `{ fixturePreflight: "failed" }` in the evidence (`fixture-preflight.ts:38-46`). Nothing is recorded in `.dojorc` or `web.json`.
3.  **Seed.** For an earlier lesson: `channel.save` with `solved`, `channel.check` (no session, so the card is "dropped"), assert `report.complete`, `channel.advance`; evidence `{ lessonId, fastForward: true, observation }` (`authoring-handoff.ts:126-135`).
4.  **Teach the last lesson.** `channel.open(courseId, lessonId)` gives the session and the begin turn (stage `introduction`); evidence `{ lessonId, sessionId, model }` and `<lessonId>-instructions.md` written with `senseiSessionInstructions({ mode, guidance: DOJO.md, lesson: { source: SENSEI.md, fragmentIds } })`. Then, each turn at least `turnIntervalMs()` after the previous one: `uncertainty`, `unfamiliar-terminology`, `misconception` (`send` of the fixture's text); `save(wrong)` and two `check`s with their report turns (`failure-1`, `failure-2`; each observation must fail and count as attempt 1, then 2); `frustration` and `independence` (`scriptedLearner`); `save(solved)`, `check` (`success`, must pass); `review`, the learner's own reply through `roles.reply` once the first completion question has been answered (up to two replies, `authoring-handoff.ts:283-291`).
5.  **Questions.** A turn that pauses with questions: if every question's options are Review, Move on and Pause (case-insensitive), the trial answers Review the first time and Pause the second (the taught lesson is the request's last, so, as in `authoring-handoff.ts:153,194`, there is no next lesson to move on to); otherwise `roles.answer` (at most four teaching-question replies) and every answer must name an offered option unless `allowOther`. The answer is sent with `channel.answer`, and the resumed turn is followed the same way. Each is recorded as `{ lessonId, duringStage, questionKind, questions, selections }`, and a completion as `{ lessonId, completionChoices, navigatedLesson }`.
6.  **After every turn**, once the channel reports it done (the record has left `working`, so the hooks' verify has run, fact 10). The turn fails the trial (`TeachingFailure`) when `takeNotices(trialRoot, courseId, lessonId)` returns a violation ("Sensei edited learner code"), or the installed material differs from step 1's ("Sensei changed installed material"). It is an infrastructure failure when the turn's outcome is `failed`, when `budget` is set ("The trial reached its usage limit."), or when its text carries a provider error (`authoring-handoff.ts:231-233`). Evidence per turn: `{ lessonId, stage, learnerMessage, contextBeforeTurn: dojoLessonContext(readLesson(...)), parts, sourceBefore, sourceAfter }`.
7.  **End.** Two completion choices must have been made, or `TeachingFailure` (`authoring-handoff.ts:294`). The last evidence entry is `{ deterministicLifecycle: "passed" }`, or `"failed"` with the error. In `finally`: the evidence is written, the open turn is cancelled when the signal aborted, and `stopHost(trialWorkspaceId, agent)` stops the trial's Sensei host (design, "Persona hosts").

`evaluations.run` wraps it: refuse with `EvaluationRefused` when consent is off (`not_enabled`), when the draft's agent is not offered (`agent_not_offered`), or when a trial for the same draft runs (`evaluation_running`); `checkEvaluationRequest`; then it makes the evidence folder, builds `oneShotRoles({ ..., evidenceRoot })`, and runs `withAllowance(..., signal => evaluateAuthoredCourse({ root, lessonIds, signal: AbortSignal.any([signal, AbortSignal.timeout(trialTimeLimitMs)]), teachingPolicy: senseiEvaluationPolicy(mode), priorLessons: "seed-completion", judge: roles.judge, trial: signal => runTrial(...) }))`. `MaterialFailure` maps to `preflight_failed`, the allowance's exhausted error to `allowance_exhausted`.

## Decisions made in this plan

1.  **The trial talks to Sensei over the UI server's own HTTP routes, through a `TrialChannel`.** D15 asks for the learner's own entry points; going through `/api/v1` and the lesson routes runs the launch-token check, the pre-delivery hook (guard windows, `firstMessage`), the held-report rules and the lesson socket's server side exactly as a page does. The trial's script logic is tested with a fake channel; the HTTP channel is tested whole by `test:evaluation`. The design names one `trial.test.ts`; the two refusals it lists belong to `evaluations.ts`, so they are in `evaluations.test.ts` next to it.
2.  **The trial script is `authoring-handoff.ts`'s, unchanged in its stages, with the struggling learner only.** The design points at that script for the cost (`agent-runtime.md`, "Evaluation"); the worker's `--evaluate-heldout` (confident learner) and `DOJOFOO_EVAL_FIXTURE_PATH` replay were developer options outside the product (fact 1); D10 gives the product one learner. The design's cost sentence ("one learner one-shot per scripted learner turn") does not match that script, whose scripted turns are fixed text; commit 12 corrects it to what the trial spends.
3.  **One or two lessons, one trial.** The design says an evaluation trial is one attempt on one lesson and asks how a multi-lesson request runs; today's two-lesson request seeds the first lesson as completed and teaches the second (`authoring-handoff.ts:126-135`), and `readTeachingEvidence` checks exactly that (`run.ts:80-82`). So every trial teaches one lesson; an earlier lesson in the request is seeded in the same install. `priorLessons: "teach"` (an environment option of the worker, `teaching-eval.ts:24-25`) is not offered.
4.  **The role calls live in the UI server (`roles.ts`); authoring keeps prompts and parsing.** The design deletes `learner-response.ts` and `generateLearnerFixtures`, which are the `HarnessAgent` halves; their prompts and validation move into `learner.ts` and `learner-fixtures.ts` as pure functions, and the model calls are `oneShot` in the composition root, where the agent, model and state folder are known.
5.  **Judges are two isolated one-shots on the course's agent and model; the CLI judge pair stays for dev evals.** D10 puts every role on the course's agent; `decidePanel` needs two distinct judge ids (`panel.ts:20`), so they are `judge-1` and `judge-2`. `judgeMaterial` and `localJudges` keep serving the live tests and dev evals (fact 4), which the design's accepted risk "dev evals pick other models" relies on.
6.  **Fixture verification uses `kata --check --no-record`.** The worker ran the tests in-process without recording (`fixture-preflight.ts:8-10`); the UI server checks through the CLI, which records a passing check as completion (fact 11), and a recorded completion of the taught lesson would break the trial. A flag that only skips the writes is the smallest change.
7.  **The ceiling is a `sessionUsage` function that reads `runtime.json`; the values are an estimate.** `limits` is static in the agent definition, but `sessionUsage` is loaded from the module at run time (fact 8), and the host already writes `runtime.json` before every start. 3 000 000 new input tokens or 300 000 output tokens is about ten times a trial's eleven Sensei turns at the 32 000-token compaction budget Sensei declares (`packages/authoring/src/sensei/agent.ts:75`), which leaves room for native tool loops and stops a runaway trial. Unverified: that the callback may read a file in Eve's runtime; tier A's `usage-ceiling` settles it per agent, and tier B records per-trial tokens (design, "Non-Functional Requirements").
8.  **Evaluation trials stay out of course installations and the dashboard.** In the UI server a trial registers in the user's own state (fact 12), and two installs of one course id make the dashboard answer 409 and block `dojofoo add`. Filtering by the `evaluation-trial` kind, which only evaluation trials have, keeps learner workspaces and manual trials as they are.
9.  **The consent text names the agent and the counts.** The design asks for them: "Allow Kyoshi to run teaching evaluations on <agent>. Each trial makes one call per lesson to write practice solutions, about eleven Sensei turns, up to six simulated-learner replies and four judge calls. Up to three attempts per lesson set; subscription quota or API charges may apply."
10. **`evaluation.cancel` is a host-port method.** The design says Kyoshi's tool cancels the trial when its `abortSignal` fires and names only `start` and `status`; a cancel needs its own mutating call, keyed like the others.
11. **Failures are typed codes, and the unsupported-agent result goes.** Kyoshi's tool used error text to tell outcomes apart (`evaluate.ts:26-27`); a code survives the host-port hop. Every offered agent runs Sensei on Eve, so any of them can be evaluated, Pi included (step 5 decision 71); a draft whose saved agent is not offered (Cursor) gets `agent_not_offered` before an attempt is spent.
12. **One trial per draft, keyed by the draft's resolved folder, in a process-global map.** Route modules may load twice (`host-port.ts:31`, as its `trials` map does), and both entry points (the route and Kyoshi's tool) must see the same running trial.
13. **The trial carries the draft's model for its agent.** D10 runs every role on the course's agent; D26 keeps a last model per agent in `runtimes.json`. Copying `models[agent]` lets Sensei's default conversation and the one-shots use the model the author chose; without one, every role uses the agent's default.
14. **The recorded policy is Sensei's on Eve.** The report's hash must describe the instructions that taught (`run.ts:138-141`); the ACP policy in `lesson/instructions.ts` no longer teaches. Passing reports from before this step become stale ("The teaching instructions have changed…"), which D9 allows.
15. **`<lessonId>-instructions.md` is what one Sensei session is told.** `readTeachingEvidence` hands every such file to the judges (fact 3); on Eve the persona instructions and the per-session course instructions together are that text.
16. **The evidence folder stays `<draft>/.dojo/handoffs/run-*`.** Reports already point there (`report.trialDirectory`), and the folder sits with the draft's other evaluation state.
17. **A guard violation reaches the trial through the guard store's notices.** The trial opens no socket, so `reportViolation` keeps a notice (fact 10); taking it after each turn both fails the trial and leaves no stale notice for a later page. The file content alone cannot show it: the guard has already restored the file.
