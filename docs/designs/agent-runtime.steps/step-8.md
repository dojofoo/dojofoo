## What this step delivers

The code is regrouped into the two packages the design names, and nothing a user sees behaves differently.

*   `@dojofoo/harness` (`packages/harness`) is today's `@dojofoo/agent` (`packages/agent`), plus the session API from `@dojofoo/agent-api` under `src/api/`, plus the message projection from `packages/authoring/src/eve/messages.ts`. It runs and connects agents: Eve, the adapters, model calls, persona hosts, the lifecycle hook, the host port, the session API and the browser's chat projection.
*   `@dojofoo/agents` (`packages/agents`) is today's `@dojofoo/authoring` (`packages/authoring`): the two persona builds, their instructions, tools, skills, templates, prompts, Sensei contracts, evaluation logic, scaffold, draft service and model discovery. Its HTTP routes (`src/server/routes.ts`) move into the UI server at `packages/ui/src/server/authoring/routes.ts`.
*   The harness exports three named groups of entry points: the closed set of nine for the UI server, the CLI and the browser (G4); Eve's own subpaths for persona builds and evals (G4); and four test entries. Lint rules keep the UI and the CLI on the closed set and the test entries in tests.
*   `pnpm lint:names` fails on any old package name or folder. The pending changesets name the new packages, and one changeset describes the whole series (`agent-runtime.md:646`).
*   Tier B (real models, the user's own logins) gets its runner and its cases, and runs once on the branch head before the PR merges.

The `/agents` route keeps meaning coding agents (D4); nothing in this step touches it.

## Decisions made in this plan

1.  **The closed set gathers the harness's own subpaths into `./adapters` and `./persona`; files do not move.** G4 names nine entry points for the UI server, the CLI and the browser, and the persona-build set is Eve's subpaths, so the harness's other own subpaths must fold into the nine. `./adapters` takes what makes a model call (adapters, the harness model, `HarnessAgent`, the local sandbox, `oneShot`); `./persona` takes what runs a persona host (host, lifecycle hook, process groups, file guard, read-only settings). `read-only.ts` goes to `./persona`, not `./adapters`, because the UI server loads `models.ts` (fact 18), which uses it, and `./adapters` would load every adapter package into the UI server's process. The UI server statically imports `./persona` (for process groups and the file guard), so its bundle gains `persona-host.ts`, `lifecycle.ts`, `read-only.ts` and Eve's `defineHook` module, none of which acts at import (fact 2); `test:lesson`, `test:package` and the browser specs run that bundle. `./adapters` stays out of the UI's static graph, as today. What `./adapters` changes in load behaviour is in decision 28.
2.  **`./server/production`, `./server/build` and `./eve/package.json` stay as persona-build entries.** They are Eve's own `startProductionServer`, `buildApplication` and package manifest, which upstream Eve does not export; only `verify-agent.mjs`, `build-agent.mjs` and Eve-locating scripts use them (fact 3). Folding `buildApplication` into `./server` would make the build child load Eve's development server module too.
3.  **Test entries are a third, named group.** `./api/fixtures` starts a real Eve development server and `./host-port/fixture` an HTTP server; putting them in `./api` or `./host-port` would put test servers into the UI server's bundle. `./scripted-harness` is a scripted HarnessV1 for guard cases, and `./local-history` exists only for the harness's packed-consumer test. A lint rule keeps them in tests, fixtures, the agents' scripts and the evals.
4.  **Each package is moved and renamed in separate commits.** A folder move with no content change shows every file as a 100% rename; the name change then shows as ordinary line diffs in files that did not move. Doing both at once would push small files (a tool file of three lines with one changed import) under Git's rename threshold, the problem Alternative K names. Edits inside a moved folder therefore wait for the next commit.
5.  **The session API's fixture runs in a temporary folder and links the harness itself, before the move.** The fixture Eve project found `@dojofoo/agent` through `packages/agent-api/node_modules` (fact 5); inside the harness there is no such link (fact 6). A link created by `startEve` is what `prepare.ts` already does for managed apps. Creating it in commit 2, in the unmoved file, keeps new behaviour out of a moved file (D14), and a run folder outside the package avoids a link from inside the harness back to the harness. dependency-cruiser cannot follow a link made at run time, so the fixture's folder is exempt from `dojofoo-imports-resolve`.
6.  **`@dojofoo/agent-api`'s changelog is deleted and the moved changelogs are retitled.** The harness has one changelog; agent-api's only entry is a dependency bump (`packages/agent-api/CHANGELOG.md`), kept in Git history. Changesets keeps a changelog's first line (fact 12), so `packages/harness/CHANGELOG.md` and `packages/agents/CHANGELOG.md` get the new names as titles; their history is not edited. `eve-1.md` loses its `@dojofoo/agent-api` line, since the harness's `minor` already covers the API.
7.  **`@tanstack/ai` moves with the message projection, as a harness dev dependency.** `messages.ts` imports only its types (fact 7), so nothing loads it at run time; the UI's type check resolves it from the harness's folder. The agents package has no other user of it.
8.  **Elysia and `exact-mirror` are harness dev dependencies.** The session API is TypeScript source that only the UI's build and the tests load, and the UI's server output bundles Elysia (fact 5). As dependencies they would be added to the published CLI's dependency list by `prepare-package.mjs:32-35`, which merges the harness's dependencies, without being used there. `eve` is a dev dependency of the harness for the same reason.
9.  **`service.ts` and `files.ts` stay in `@dojofoo/agents`; only `routes.ts` moves to the UI server.** The design moves `src/server/*`, but the CLI and the evals use `service.ts` (fact 8), the evals may not import the UI, and the CLI does not depend on the UI server's code. `files.ts` is imported by `service.ts`. What leaves the persona package is the HTTP layer; the draft model stays with the evaluation logic and the scaffold it calls, which the design's list for `@dojofoo/agents` already includes. The folder keeps its name (`src/server/`), so its exports and tests do not move.
