# Teaching calibration

`teaching-moments.json` tests whether the existing judges recognize useful
teaching. It does not run Kyoshi, simulate learning, or certify a lesson.

- `user-report`: a rejected response or a labelled reconstruction from the user's history.
- `proposed-reference`: a candidate good response; not a human-approved gold standard.
- `authored-counterexample`: a deliberately bad contrast.

Review the proposed references before treating this as a golden dataset. Labels
apply only to the listed criteria; an excerpt cannot pass a whole lesson.
The judge receives context and dialogue, never the expected labels or notes.

From `packages/authoring`, validate the data without model usage:

```sh
pnpm exec vitest run src/evaluation/teaching-moments.test.ts
```

Run selected cases against the two existing judges (paid/subscription usage):

```sh
DOJOFOO_EVAL_TEACHING_CALIBRATION=1 \
DOJOFOO_EVAL_CASES=opening-stub-recital,opening-concrete-purpose \
pnpm exec vitest run src/evaluation/teaching-moments.test.ts --fileParallelism=false --maxConcurrency=1
```

Omit `DOJOFOO_EVAL_CASES` to run every case. Each case makes two judge calls.
Inputs and raw results are saved under the printed temporary directory. When a
judge disagrees, inspect both the label and its reasoning before changing any
teaching instructions. Judge agreement on proposed references is not human
validation, evidence of learning, or an end-to-end acceptance pass.

## Initial observation

On 2026-10-15, all seven cases matched their scoped expectations under both
existing judges (14 judgments, `sensei-chain-v9`). This includes allowing the
missing-principle explanation and rejecting the exact repair. No authoring or
learner-model calls were needed.

This checks a small set of obvious contrasts, not subtle teaching quality.
The proposed references still need human review. Do not use this result to
claim that authored lessons teach well or that the judges are fully calibrated.
The next check is whether these cases discriminate between actual lesson
variants, with the candidate responses generated by the production Sensei.

## Focused production check

`packages/ui/src/server/lesson/authoring-focused.live.test.ts` runs three real
Sensei turns against a saved largest-number lesson: introduction, a question
about running state, and a nearly correct learner attempt with an initialization
gap. It reuses the production trial runner and does not generate a new course
or simulate a learner with another model.

Run it explicitly with `DOJOFOO_EVAL_FOCUSED=1`, `DOJOFOO_HANDOFF_COURSE` pointing
to the saved course, `DOJOFOO_EVAL_LESSON_ID` selecting its lesson, and the normal
`DOJOFOO_HARNESS`, `DOJOFOO_HANDOFF_MODEL`, and `DOJO_CLI` settings. It is skipped
by default. The saved evidence includes the exact production instructions.

The first run on 2026-10-15 passed engagement, learner grounding, adaptation,
and solution withholding under both judges. Both returned insufficient evidence
for a whole-lesson pass. Full completion and transfer remain untested by this
short check; its lifecycle marker is deliberately `not-evaluated`.

## Lesson-specific learner questions

From `sensei-chain-v10`, new generated fixtures include `uncertainty` and
`terminology` messages tied to the lesson and the learner's prerequisites.
They use the existing fixture-generation call, not extra model turns. The
generator receives no SENSEI files or platform teaching policy. Tests are
available to construct code fixtures, not as something the learner can quote.

Older recorded fixtures keep their original scripted questions when replayed.
Do not compare those replays to the new simulation as if the inputs were equal.
