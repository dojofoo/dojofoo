# 0112: Match the Pages composer to native coding-agent capabilities

Parent: 0100/0105/0106/0107. Status: ready for implementation; local review only.

Goal: use the current Pages Composer everywhere, with a coding-agent picker first, that agent's actual models second, and a working plus control for supported image/file attachments. Sensei and Kyoshi remain conversation roles. No forked composer or archived template.

Evidence from current source: Composer accepts one static agent and turns its picker into a single checked item. Its file input retains only filenames and onSend accepts text only. Pages learner supplies neither agent nor native-looking model choices; Pages authoring also retains the general assistant controls. Native kata and AuthoringChat explicitly disable attachments and label the selected agent Sensei/Kyoshi. Kata model options already come from the session's advertised configuration, including provider groups. The lesson session-start route already accepts a validated harness. Interactive conversation bindings retain a harness and model, but no first-class agent selection route exists. Authoring native catalogs are available through /api/authoring/models?harness=...; runtime-turn tests already prove next-turn model selection and retained history. ACP learner registry supports Codex, OpenCode, Cursor, Grok and FX and explicitly rejects Pi; Pi is supported for authoring.

Boundaries: extend the shared Composer through controlled capability props, retaining all existing callers and queue/cancel/draft ownership. Supply story-only agent/model catalogs through Pages controllers, never production defaults. Native owners supply actual harness identity, capability limits and model configuration. Model family does not determine coding-agent identity. Keep the actual native conversation ID, transcript, queued work, pending questions, dirty editor, course progress and failure state through presentation changes. Do not silently replace an existing interactive binding or invoke paid inference on picker changes. Selecting a different coding agent must use the existing explicit session-start boundary where available; preserve the old session and its history. Inspect native SDK attachment capability and message shapes before introducing a production attachment path. A filename chip alone is not an uploaded attachment, and hidden dropping of binary content is unacceptable.

Implementation order: first add red tests and a controlled selectable-agent seam to the existing Composer, then update current Pages stories with agent-owned model catalogs and keyboard/pointer behavior. Connect kata harness/model controls to existing native routes and advertise unavailable choices with an honest reason. Derive interactive and authoring controls from their existing runtime/session contracts before adding the minimum missing ownership-preserving route. Then carry actual attachment content through the same controller boundary, test removal/retry/queue behavior, and encode only formats advertised by each native adapter. No new package dependency, mock success or invented model availability.

Gate: red-first tests for the new controlled seams and production route capability contracts. Current Pages learner/authoring stories must use the shared controls in light/dark and mobile. Browser checks must select two different coding agents, show models across multiple provider families for one agent, retain plus control, and preserve draft/editor/queue/question state across choices and failures. Native loopback fixtures must inspect actual selected harness/model and received image/file payloads, assert no extra paid turn/session from discovery or rendering, and verify same-harness resume after restart. Unsupported attachment types/providers must leave an actionable error and keep the draft. Run relevant service suites, full UI/UIX non-live suites, type checks and built CLI/browser gates. Before any longer native run, state the hypothesis, probe the smallest contract and estimate the run. Preserve the 18 concurrent root audit files and user servers; no merge or release before review.

Channel: native request logs, real session IDs and persisted bindings, physical files, accepted SDK content and screenshots of the current Pages surfaces. This is remaining work, not an acceptance claim for 0100.
